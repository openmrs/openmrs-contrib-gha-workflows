# Publishing

## Names OpenMRS owns

Outside the `openmrs` organization, nothing is published unless the caller turns publishing on (see
[Turning publishing on](/community#turning-publishing-on)). Once it is on, publishing to names OpenMRS owns on public
registries fails, since that is not a supported setup.

| Ecosystem | Not published outside `openmrs` | Allowed |
| --- | --- | --- |
| npm | `@openmrs/*` and `openmrs` on `registry.npmjs.org` (or `registry.yarnpkg.com`) | Any other name; any name on another registry |
| Maven | `mavenrepo.openmrs.org`; `openmrs.jfrog.io/artifactory/{modules,snapshots,releases}`; `org.openmrs*` groupIds on Maven Central | Any other repository, including other paths on `openmrs.jfrog.io` |

A fork of an OpenMRS module publishes once you rename its packages (or change its POM's `<distributionManagement>`) to
targets you own.

## npm

### Authentication

The release workflow accepts either:

- **Trusted publishing (recommended).** No long-lived token. On npmjs, configure a trusted publisher for each package
  naming your repository, the **caller** workflow file (for example `ci.yml`) and, if you use one, the GitHub
  environment. Then:
  - grant the calling job `id-token: write`;
  - use Yarn 4.10.3 or later (earlier versions cannot exchange the token for scoped packages);
  - set `publish_environment` to the environment named on npmjs;
  - keep each package's `repository.url` pointing at the publishing repository, since npm checks provenance against it.
- **A token**, passed as the `NPM_AUTH_TOKEN` secret. If you keep it as an environment secret, name it
  `NPM_AUTH_TOKEN`, set `publish_environment` to that environment, and still pass the secret from the caller.

Without either, publishing fails before anything is built. With `publish: false`, pre-releases are skipped.

<Callout type="warning">
Renaming the caller workflow file breaks trusted publishing until the npm configuration is updated, and restarts
`github.run_number`, which numbers pre-releases. A new file can collide with pre-release versions already on npm.
</Callout>

### Registries

Packages publish wherever Yarn's configuration sends them: a package's `publishConfig.registry`, then the scope's
`npmPublishRegistry` in `.yarnrc.yml`, then the top-level `npmPublishRegistry`, then `npmRegistryServer`. Set
`npm_registry_url` to override the top-level registry from the workflow.

The workflows are tested against npmjs. Other registries (GitHub Packages, Azure Artifacts, Verdaccio and so on) are
supported but not tested; please [report problems](https://github.com/openmrs/openmrs-contrib-gha-workflows/issues).

## Maven

SNAPSHOT deploys and releases go to the repositories in the POM's `<distributionManagement>`, or to
`maven_snapshot_repository_url` / `maven_release_repository_url` when set. They authenticate with the
`MAVEN_REPO_USERNAME` and `MAVEN_REPO_API_KEY` secrets, which map to the inferred server IDs. A deploy without
credentials fails. SNAPSHOTs deploy only when `deploy_snapshots` is true, and releases only run when `publish` is true;
outside the `openmrs` organization both default to false.
